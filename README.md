# Автоматизация и стандартизация процесса документирования аналитики (Analytics Documentation Framework)

## Задача, которую решает проект

Основная цель данного проекта — **создание надежного, стандартизированного и машиночитаемого фреймворка для документирования аналитики**, который устраняет разрыв между человекочитаемыми аналитическими требованиями (ТЗ системных аналитиков) и автоматизированной технической реализацией (кодом дата-инженеров). 

Проект решает следующие ключевые проблемы:
1. **Перевод ТЗ в Data Contracts**: Обеспечивает методологию и шаблоны для бесшовной трансформации аналитических отчетов из Confluence/Jira (в формате Markdown) в строго типизированные цифровые контракты данных (Data Contracts) в формате YAML согласно Open Data Contract Standard (ODCS v3.1.0).
2. **Стандартизация логики трансформаций**: Внедряет единый стандарт описания источников, типов операций (read, filter, join, aggregate и т.д.), условий соединений и выражений, полностью совместимый с парадигмой **Spark DataFrame API** и SQL.
3. **Автоматизация ETL и Data Lineage**: Позволяет автоматически валидировать входные требования, отслеживать происхождение данных на уровне полей (Lineage) и использовать машиночитаемые схемы для автоматической генерации кода пайплайнов загрузки витрин данных.

### 1. `data_contract/`
Основная директория для работы с цифровыми контрактами данных, исходными ТЗ на витрины и эталонными шаблонами.

* **`confluence/`**
  Содержит исходные аналитические документы и технические задания на разработку витрин данных, экспортированные из Confluence (в формате PDF). Служит отправной точкой (источником бизнес-требований) для формирования контрактов.
  *Примеры файлов:* ТЗ по витринам комиссий, физических лиц с согласиями для налоговых вычетов, партнеров ЮЛ и родственным связям.

* **`partner_tdp/`**
  Директория с конкретной реализацией дата-контрактов и SQL-кода для **Витрины партнеров юридических лиц** (`partner_tdp`).
  * **`partner_tdp_*.yaml`** — Модульные файлы, описывающие отдельные блоки контракта (основные метаданные, входные параметры, стратегия загрузки, качество данных, схема, системы-источники и пошаговый флоу трансформации) для версий v1 и v2.
  * **`partner_tdp_v1.yaml` / `partner_tdp_v2.yaml`** — Итоговые собранные контракты витрины.
  * **`*.sql`** (`init.sql`, `partner_tdp.sql`, `partner_tdp_v2.sql`) — SQL-скрипты для инициализации структур и DDL/DML трансформаций витрины.

* **`templates/`**
  Директория стандартов и эталонных шаблонов для системных аналитиков и инженеров:
  * **`analisisy_v1.md`** — Единый Markdown-шаблон описания витрины данных для аналитиков. Задает жесткую структуру ТЗ: история версий, источники, пошаговые трансформации с указанием Enum-операций, маппинг полей и критерии приемки.
  * **`data_contract_odcs_template.yaml`** — Базовый шаблон контракта данных, соответствующий спецификации ODCS v3.1.0.
  * **`data_contract_template.yaml` / `data_contract_template_v1.yaml`** — Расширенные шаблоны контракта данных, адаптированные под кодогенерацию на Spark DataFrame API (включают секции pushdown-предикатов, алиасов шагов, join-условий и lineage).
  * **`data_contract_template/`** — Поддиректория с декомпозированными (модульными) YAML-шаблонами по каждому разделу контракта для удобства автоматической сборки.

* **`partner_tdp_v1.yaml`** (в корне `data_contract/`)
  Консолидированный рабочий пример полноценного контракта данных, демонстрирующий объединение стандарта ODCS и детального алгоритма загрузки на Spark DataFrame API.

### 2. `sdd-project-root/`
Структура репозитория, организованная согласно подходу **Schema-Driven Development (SDD)**. Предназначена для управления жизненным циклом схем, хранения контекста AI-ассистентов и базы знаний RAG.

* **`.ai-context/`**
  Директория контекста и системных промптов для AI-ассистентов (LLM), помогающих в кодогенерации и валидации:
  * **`rules/`** — Набор жестких инструкций и ограничений, разделенных по доменам: `00_general`, `01_communication`, `02_configuration` (содержит соглашения об именовании `naming_conventions.md`), `03_sources`, `04_transformations`, `05_persistence`, `06_data_contract`.
  * **`skills/`** и **`templates/`** — Навыки и шаблоны промптов для специализированных задач LLM.

* **`contracts/`**
  Целевое хранилище утвержденных и активных версий контрактов данных проекта.

* **`infrastructure/`**
  Конфигурации для интеграции и деплоя:
  * **`deployment/`** — Сценарии и манифесты развертывания пайплайнов данных.
  * **`mcp-configs/`** — Настройки серверов протокола **Model Context Protocol (MCP)** для предоставления LLM безопасного доступа к ресурсам окружения.

* **`rag-repository/`**
  Локальная векторная/файловая база знаний для RAG-системы:
  * **`constants/`**, **`history/`**, **`schemas/`** — Хранилище общих констант, истории сгенерированных решений и схем источников данных для обеспечения контекстной осведомленности AI.

* **`requirements/`**
  Директория для хранения исходных бизнес-требований и ограничений.

* **`.gemini.md`**
  Манифест и правила взаимодействия со средой для модели Gemini.

---

### 3. `mcp_servers/`
Директория для реализации локальных серверов Model Context Protocol (MCP). Позволяет инструментам искусственного интеллекта стандартизированно обращаться к локальной файловой системе, базам данных или механизмам проверки контрактов.

---

### 4. `.docker/`
Инфраструктурные файлы для быстрого развертывания локальной изолированной среды разработки и аналитики.
* **`Dockerfile`** — Инструкции для сборки Docker-образа со всеми необходимыми инструментами аналитика/инженера.
* **`docker-compose.yml`** — Описание конфигурации сервисов для запуска контейнера.

---

### 5. Корневые файлы проекта

* **`Makefile`**
  Утилита для удобного управления проектом через терминал. Доступные команды:
  * `make up` — Запуск локальной Docker-среды аналитика в фоновом режиме.
  * `make build` — Сборка/пересборка Docker-контейнера.
  * `make down` — Остановка контейнеров.
  * `make clean` — Полная очистка и удаление созданных образов/контейнеров.
  * `make shell` — Быстрый вход в интерактивную bash-консоль запущенного контейнера.

* **`sdd_setup.sh`**
  Исполняемый Bash-скрипт для первичной инициализации проекта. Автоматически создает всю необходимую иерархию папок внутри `sdd-project-root/` и базовые файлы-заглушки.

* **`.gitignore`**
  Стандартный файл исключений Git для предотвращения попадания временных файлов, локальных логов и сборок в удаленный репозиторий.
